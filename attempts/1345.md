## Statement and interpretation

A corrupted file consists of records introduced by @ and their integer record number, and ends with $ and the total record count. Each address originally had the fields Id-no, Name, Location, Post-office, and optionally Area, in that order. Fields have been permuted as contiguous blocks. A line ends in a semicolon; Id-no, Name, and Post-office have exactly one such line, while Location and optional Area have one or more. Each record is at most 1000 characters. The input says at most ten test cases but shows no leading case count, so the submitted parser read records/files until EOF.

The output puts a count of options after each @ record marker. Each option has its one-based number rendered as that many slash characters on a line, followed by the reordered original text. Options sort lexicographically, with newline below every other character. The $ footer adds the number of records with at least one valid recovery. Every blank and newline after a field's terminating semicolon belongs to that field, so those bytes must move with it.

The implemented lexical rules were these:

- Words are maximal sequences of ASCII letters and digits. Separators are whitespace, comma, and hyphen; other characters invalidate a line. Leading whitespace is ignored for validation, but preserved for output.
- Id-no accepts alphanumeric words, no comma, and requires at least one hyphen. Each separator has at most one hyphen, and a trailing hyphen is rejected.
- Name accepts alphabetic words only, at least two words, no hyphen, and at most one comma. A trailing comma is rejected. With a comma, the nonempty words before and after it stand for surname and name parts; without it the final part is the surname.
- Location accepts any alphanumeric words, no hyphen. The first version rejected repeated or trailing commas within each semicolon line. The third version allowed any commas in separator strings, including trailing commas.
- Post-office accepts one or more alphabetic words followed by exactly one six-digit numeric word. Separators between name words must be whitespace. Between the last name word and the code, whitespace or hyphen is allowed. Its last separator must be whitespace. The implementation permitted multiple hyphens in that final name/code separator, an untested edge.
- Area accepts alphabetic words whose first letter is uppercase, no hyphen, and at most one comma following each word. It allows a comma at the end of a line.

These are interpretations, not settled judge semantics. In particular the statement's handling of punctuation, the exact structure/minimum size of the two Name parts, whether there is hidden test-case framing, and whether different field boundaries yielding identical text count as different options remain unresolved.

## Algorithm and implementation details

The parser read the entire input with getline, removed a terminal carriage return per physical line, and appended a newline after every getline. Thus it normalized CRLF and also injected a newline if the final physical input line lacked one. It consumed each @ header through its newline. Inside a record it formed line strings by reading through a semicolon and then all following whitespace up to the next non-whitespace character. It stopped on @ or $. Headers were parsed as immediately adjacent marker/digits, without whitespace between the marker and integer. Footer recovery counts reset after each $.

Each semicolon line received a five-bit eligibility mask from the validators above. Depth-first search tracked the next line index and the set of fields already assigned. For each unused field, it tried all eligible nonempty contiguous prefixes from that index, except the three one-line fields were forced to stop after one line. At end of record, a branch was accepted if the mandatory four fields were assigned. The recovered text was concatenated in normal field order, with Area omitted if unused. All field buffers were cleared when backtracking. No source was archived because no attempt was accepted.

The first and third submissions accumulated recovered strings in an ordered set, deduplicating identical bytes. The second used a vector, sorted it, and retained duplicate strings from distinct assignments. Neither interpretation accepted. A separating example for this uncertainty is an original record containing Id-no and Name, then two or more alphabetic lines which can be divided between Location and Area in several ways, followed by Post-office: several valid boundaries can concatenate to identical output text.

## Verification and its limits

The official sample passed byte-for-byte for all three versions. It contains an impossible first record with no Id-no hyphen and a second record admitting two recoveries. Removing Area recognition makes the sample fail, so it does exercise the optional field. It does not settle the other grammar choices.

For the first version, 250 random sequences of four to seven lines were compared against a separate Python reference. The reference enumerated every cut into four or five contiguous nonempty blocks and every field permutation, and checked each line with independently expressed regular expressions. The candidate line pool included hyphenated identifiers, six-digit post codes, alphabetic names with and without commas, numeric/alphanumeric locations, uppercase and lowercase words, and an Area line ending in comma. All comparisons passed. This certifies the partition enumeration for those lexical assumptions, not the assumptions themselves; the regex reference shared the same reading of the prose. A separate four-field witness checked preservation of leading blanks and multiple blank lines after a semicolon.
