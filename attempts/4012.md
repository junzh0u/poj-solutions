## Statement

POJ's page for 4012 has always had blank Description/Input/Output sections (confirmed via
raw `curl`, not just page rendering). The title, "Black Square", plus the three sample
input/output pairs baked into the (also otherwise empty) sample block, match problem B of
the ACM ICPC 2011–2012 NEERC Northern Subregional Contest exactly — confirmed against the
official contest PDF (`https://neerc.ifmo.ru/archive/2011/northern/problems.pdf`) and its
`problem.xml`/`check.dpr` judging package, both of which a prior agent had already
downloaded into the scratchpad along with `tests/01`..`93` (each a single input file plus
its `.a` answer file, no `T` header, no multi-case framing — this is NEERC's original,
single-case-per-file contest format).

The problem: an m×n grid is painted white, then one axis-aligned black s×s square is
painted onto it, then the grid is cut into m horizontal 1×n stripes and only stripe k
survives. Given m, n, s, k and stripe k's content (a string of `.`/`*`), decide whether the
original square's position can be uniquely reconstructed (`Unique`), is ambiguous among
several positions (`Ambiguous`), or is inconsistent with any placement (`Impossible`).
NEERC's stated bounds: 1 ≤ m, n ≤ 5000, 1 ≤ s ≤ min(m,n), 1 ≤ k ≤ m; POJ's own limits (1000ms
/ 65536K) are tighter than NEERC's (3s / 256MB) but that alone says nothing about POJ's
actual n/test-count, since POJ commonly retightens limits just because a judge is faster.

## Algorithm

Let the square's top-left corner be (r, c), with 1 ≤ r ≤ m−s+1, 1 ≤ c ≤ n−s+1. Row k is
covered by the square iff r ≤ k ≤ r+s−1, i.e. r ∈ [max(1, k−s+1), min(k, m−s+1)] — call this
range's size `coveringCount` (always ≥ 1, since s ≤ m guarantees the range is non-empty).

- If the given row contains any `*`: it must be exactly one contiguous run of length s
  (otherwise no placement produces it → `Impossible`). That run's start fixes c uniquely; r
  ranges over the covering range, so the answer is `Unique` iff `coveringCount == 1`, else
  `Ambiguous`.
- If the row is all `.`: the square's row-range must miss row k entirely, so r ranges over
  the `(m−s+1) − coveringCount` *non*-covering positions, and c is free among `(n−s+1)`
  choices independent of r. The placement count is the product of those two factors; it's 0
  iff every r covers row k (`Impossible`), 1 iff both factors are 1 (`Unique`), else
  `Ambiguous` — checked by comparing the two factors directly rather than forming the
  (possibly large) product.

This is O(1) beyond a single linear scan of the row to find its run structure, i.e.
O(total input size) overall for any number of test cases — already asymptotically optimal
for a per-row classification, so no further algorithmic improvement is possible; the run's
task was to look for one, and none exists.

## Verification

- All 93 official NEERC tests (`black/tests/01..93` + `.a`, CRLF answers stripped before
  comparison) pass exactly, including the three published samples.
- 3000 randomized trials (m,n ≤ 8) against a genuine brute force (`brute.cpp` in a prior
  agent's scratchpad, reused) that reconstructs every candidate placement's *full* row
  content and compares it byte-for-byte to the given row — a much stronger oracle than the
  shape-only reasoning above, so agreement isn't just re-deriving the same rule — all
  agreed.
- Compiled clean under `g++ -std=c++98 -pedantic -Wall -Wextra -O2` with no warnings, and
  swept under `-fsanitize=address,undefined` across all 93 tests plus edge cases (empty
  stdin, no trailing newline) with no reports.
- A local stress input of 2,000,000 tiny test cases (42MB total) — testing the theory that
  POJ concatenates far more cases than NEERC's single-file format implies — ran in **0.05s**
  under a hand-rolled `fread`-buffer parser, versus 11.4s under naive `cin`/`printf`. This
  ruled out data volume as remotely plausible once the AC evidence below came in (accepted
  runs use 92–160K of memory, incompatible with tens of MB of input), but the timing gap is
  recorded here since it drove the middle two submissions.

## Where this stalls

Submission #5 cannot be explained by any theory this run tested: it is not looping, not
waiting on EOF, not doing meaningfully more work than the smallest imaginable correct
program for this task, and it is verified byte-for-byte identical to what reached POJ (SHA-256
match between the local file and the base64 payload decoded before every submit). A program
this small timing out at 1000ms on a judge that has run comparable programs in the tens of
milliseconds is very hard to reconcile with anything other than the judge, this problem's
checker, or its current test data being broken right now, even though there is no other
account's recent submission to confirm that contemporaneously (the last non-self submission
to 4012 of any kind was the 2024-12-24 Accepted run). If revisited, the highest-value first
step is simply re-submitting the exact `25207065` source unchanged, or resubmitting the
archived-elsewhere-verified `24869247`/`23172444` style approach, purely to see whether the
judge's behavior on this problem has changed — a distinct hypothesis from anything already
spent here would be needed before trying a sixth variant. `solutions/4012/test_data/` (left
by the prior agent, `4012.in`/`.out` for the sample and `4012-neerc-max.in`/`.out` for
NEERC's stated worst case m=n=5000, s=4280, k=1898) is uncommitted but kept — both pairs are
genuine NEERC-sourced data and remain useful for any retry.
