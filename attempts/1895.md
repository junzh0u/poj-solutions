# 1895 — Bring Them There

## Interpretation and algorithm

There are at most 50 stars, 200 undirected tunnels and 50 ships. All ships begin at S and must reach T in the minimum number of days. Each tunnel can carry at most one ship per day, including both directions together. Waiting and multiple ships at a star are unrestricted. A ship may move at most once each day. Output the minimum day count followed by a list of ship-id/destination pairs for each day.

A time-expanded integral max flow represents a star at each day, capacity-K waiting arcs, and capacity-1 arcs in both directions for each tunnel between successive layers. Increase the horizon until K units reach the destination. A simple shortest path provides an upper bound of N+K-2 days. Independent antiparallel travel arcs are a relaxation, but any pair of simultaneous opposing crossings can be replaced by one wait at each endpoint, preserving every layer balance. Cancel such pairs before decomposing the final flow into ship paths. Thus the relaxation and actual schedules have the same optimum.

The first implementation used Dinic with one persistent source and a super-sink collecting arrivals from every destination layer. The independent control translates the structure of Andrew Stankevich's original NEERC 2003 jury solution `b_as.dpr`: BFS augments a residual network stored as day/from/to flow counts; on extending the horizon, the existing flow waits at T. Its reconstruction first cancels opposing crossings and then assigns individual ship paths. All integer values fit in 32 bits.

## Verification and external evidence

The original jury archive is publicly available at https://neerc.ifmo.ru/archive/2003/archive.rar (linked from https://neerc.ifmo.ru/archive/2003.html). Within it, `archive/solutions/bring/` contains `b_as.dpr`, several other reference implementations, `checkb.dpr`, and 16 literal input files under `tests/01` through `tests/16`; later tests are Pascal generators. The jury checker verifies the optimum day count, 1 <= moves-per-day <= K, distinct ship ids each day, valid tunnels, no tunnel used twice in either direction, and every ship ending at T. No output-order constraint is present in that checker.

Both implementations generated valid schedules on all 16 literal contest inputs and agreed on their minimum horizons: 4, 1, 3, 6, 10, 13, 18, 17, 50, 50, 3, 26, 26, 27, 27, 27. These are independently computed horizons, not supplied answer files. A separate witness validator checked every emitted pair against the undirected graph and tracked ship positions; it also rejected an intentionally duplicated-ship sample. The first solver agreed with exhaustive BFS over indistinguishable-ship configurations on 220 connected random graphs with 2–5 vertices and 1–3 ships. That brute force enumerates every simultaneous action and rejects repeated undirected tunnels directly. A 50-vertex path with 50 ships returned the provable optimum of 98 days in about 0.005 seconds locally.

POJ discussion message 354163 reports that adding waiting arcs before travel arcs yields WA whereas reversing the order yields AC, although the network is unchanged. This is evidence of a possible witness-related issue, not a proven checker defect. Other read messages supplied no useful failing case. A travel-before-wait reconstruction variant was therefore tested, but also failed. The final variant reads complete instances through EOF and resets all network state; concatenated-sample validation confirmed the reset, but it also failed on POJ. The statement itself describes one instance and gives no leading count.
