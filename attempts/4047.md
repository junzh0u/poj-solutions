POJ 4047 "Garden" has no readable statement. `curl -s 'http://poj.org/problem?id=4047'` returns a
complete page shell (title "Garden", Time Limit 1000MS, Memory Limit 65536K, Total Submissions
1835, Accepted 682) but every content field is empty: the Description, Input, and Output `<div
class="ptx">` blocks, and both the Sample Input and Sample Output `<pre class="sio">` blocks, are
all empty strings. There is no image, no attached figure, nothing else on the page.

This is not a transient render issue. The Wayback Machine's earliest capture of this exact URL,
from 2013-01-22 (when the problem had only 920 submissions / 288 accepted, i.e. close to its
creation), shows the identical empty Description/Input/Output/Sample fields. Every later capture
(2013, 2017, 2019, 2022, 2025) is the same. So the statement text has apparently never been
present in POJ's served page in over a decade, not something that broke recently.

Checking neighboring problem ids confirms this is a batch data gap rather than a one-off: ids
4012 through roughly 4054 all return the same empty Description/Input/Output/Sample pattern (only
the title, limits, and submission counts render), and ids from about 4055 up return a bare "Error"
title (no page at all) for a long stretch. Ids below ~4010 have normal, fully populated statements.

The Discuss board (`curl -s 'http://poj.org/bbs?problem_id=4047'`) lists exactly two threads:
"一个很小的bug，卡我了两个小时！" (message_id=340335) and "【线段树水题】" (message_id=181447).
Both were fetched via `curl -s 'http://poj.org/showmessage?message_id=<id>'` (the correct
form, not the 404ing `message?message_id=`) and both have a completely empty `<pre>` body — only
the titles survived, no actual pitfall or example was postable to recover from them.

Tried to identify the source contest from neighboring titles, since POJ often imports a whole
contest's problems as a contiguous id block. The surrounding ids (4045 Power Station, 4046
Sightseeing, 4048 Chinese Repeating Crossbow, 4049 Chess, 4050 Necklace, 4051 Aeroplane Chess,
4052 Hrinity, 4053 World of Goo, 4054 KINA Is Not Abbreviation) look like a mixed batch: 4034-4044
match the 2012 ACM-ICPC World Finals (Warsaw) problem set (Alphabet Soup, Coin Collecting, Game
Set and Match, Guess the Numbers, Non-negative Partial Sums, Peer Review, Score Sequence, etc.),
while "Aeroplane Chess" is also HDU 4405 from the 2012 ACM/ICPC Jinhua regional online contest
(HDU 4400-4409) confirmed via a contest wrap-up post at acmicpc.info/archives/989 (via Wayback,
since the live domain is now squatted) — but that wrap-up's own problem list (A-J, HDU 4400-4409)
does not include anything named "Garden", so 4047 is not from that online round.

Found via web search that POJ 4054 "KINA Is Not Abbreviation" is mirrored verbatim on eOlymp
(https://eolymp.com/en/problems/2467, readable through the r.jina.ai reader proxy since eOlymp's
own page is a client-rendered SPA that curl can't execute) — an unrelated string/abbreviation
problem, confirming these ids really are a grab-bag of imported problems rather than one single
contest. Tried the same reader-proxy trick against eOlymp ids near 2467 (2456-2467) hoping for a
sequential offset to a "Garden" title; none matched, and eOlymp's search UI is entirely
client-side (no curl/reader-proxy accessible query endpoint), so a title search there wasn't
possible without a real browser session. Also checked Codeforces gym (Cloudflare-gated, couldn't
search), the NEERC ifmo.ru archive (403s to both curl and the reader proxy), GitHub code search
(JS-rendered, not curl-accessible) and Sourcegraph's public code-search API (zero matches for
"POJ 4047"). No mirror with the actual "Garden" statement text was found anywhere.

Net result: the problem's actual rules — what a "garden" is, what is being updated or queried,
what the output format is — are unknown, and could not be recovered from POJ itself, its archived
history, its discuss board, or any external mirror found. No algorithm was designed, nothing was
tested, and no submission was made (0/5 of the cap used), since AGENTS.md's own procedure requires
reading the statement first and explicitly rules out guessing.

A retry only makes sense if either POJ restores the missing statement text for this id range, or
someone locates an external mirror that actually has "Garden" specifically (not just a sibling
problem from the same id block, which is not sufficient — the mirrors found so far are for
unrelated titles). Neither a stronger model nor more local reasoning changes this: the blocker is
missing source data, not difficulty.
