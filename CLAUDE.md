## Claude-in-Chrome transport for the submit step

How the harness-neutral submit contract in `AGENTS.md` §3 maps onto claude-in-chrome. Only these lines should need touching when the extension or its tools change.

- Before building the payload, validate provenance: the source must carry exactly one `// Model: <the id assigned to this agent>` line. `.agents/skills/backlog-loop/scripts/build-submit-js` is the reference check — it refuses to build a payload otherwise. A wrong `// Model:` line found after Accepted costs either another submission or a falsified archive.
- Serialize the click with the shared coordinator `AGENTS.md` §"Solving several at once" calls for: with the tab open and the payload built, run `.agents/skills/backlog-loop/scripts/with-submit-lock true` (repo-root-relative — solve agents build in the scratchpad) in the foreground — it blocks until 15s after the last recorded attempt, then stamps this one — and make the guarded `javascript_tool` click the **very next** tool call, with nothing in between. Same for every retry. This is where the Claude path deviates from Codex's, which keeps the click inside the lock by running it as the helper's child: an MCP call cannot be a subprocess, and a solve subagent cannot pause to ask the parent for a grant. The reservation stamp is the whole mutual exclusion here, so if anything intervenes after it — an error, a stale tab, a sibling re-navigate — reserve again rather than clicking late. `POJ_SUBMIT_COORDINATOR_DIR` and `POJ_SUBMIT_MIN_INTERVAL` are for testing the helper, not for runs.
- Open the tab with `tabs_create_mcp`, run the whole guarded plant-and-click as **one** `javascript_tool` call, and close it with `tabs_close_mcp` on the next tool call. This transport needs **no** landing window: by the time `javascript_tool` returns, Chrome has already committed the POST. Measured 2026-08-06 by resubmitting an archived 2455 source and closing the tab as the immediately following call — run 25194696, Accepted, 3401B.
- A `javascript_tool` error or unexpected return *after* the click proves nothing in either direction. Close the exact tab on the next call as above, then read authoritative `curl` status before retrying.
- If the tools report several connected Chromes, choosing is the **parent's** job and it happens once, during preflight. Only one Chrome may hold the POJ login, so a missing submit form on the first device is not yet a verdict on the session: probe the others and pin whichever one shows the logged-in form. Unattended runs pick that way too rather than asking — `list_connected_browsers` wants a user choice, and a `/loop` parent has no user to ask. Only when no connected Chrome holds the login is it an infrastructure interruption.
- The `deviceId` is the whole pin, and the only part worth relaying: `tabs_create_mcp` takes no arguments and puts its tab in the connected browser's single MCP tab group, so there is no window or group an agent could be told to target. Every solve agent `select_browser`s with the parent's `deviceId` and never switches — not to a device that merely looks available, not because the user opened another window or profile. That device disappearing mid-batch is an infrastructure interruption.
- A stored tabId can go stale outright, not just get re-navigated: sibling churn can close the tab or reassign the whole tab group (`tabs_context_mcp` returns a different `tabGroupId`). That is churn *inside* the pinned device, not a lost pin — on any targeting error, re-run `tabs_context_mcp` and redo navigate + submit as one unit, after checking the status page in case the click already fired. This recovery works — agents that hit it have re-checked status, re-clicked, and still landed a first-submission Accept. The `problem_id` guard has separately caught a tab a sibling re-navigated, so it earns its line.
- The parent and every solve agent share **one** MCP tab group per Claude Code session, and closing its last tracked tab auto-removes the group (`Closed tab N. Group is now empty (auto-removed).`). Removing a Chrome tab group does **not** close the tabs inside it — it ungroups them, and `tabs_close_mcp` then refuses them (`Tab N is not in this session's tab group`), so an orphaned tab is beyond every tool here and only the user can close it. Concurrent agents make this routine rather than rare, because the auto-remove decision races sibling `tabs_create_mcp` calls. So the **parent holds a keepalive tab** in the group from before the first agent spawns until after the last one reports, and closes it last: a group that never reaches zero tabs is never auto-removed. Measured across two five-agent batches: without the keepalive, 9 tabs created and 4 orphaned; with it, every tab closed and the group auto-removed exactly once, on the parent's own final close, which is where that removal is harmless.
- `build-submit-js` prints the payload base64-encoded, which is not what `javascript_tool` wants. Decode it to a file (`... | base64 -d > <scratch>/<id>/payload.js`), `Read` that file, and pass its exact contents as the call's `text`.
- The extension blocks `document.cookie` reads — this is why curl cannot borrow the session and the post happens in-page at all.
- Plain `atob` is the whole payload path. The gzip variant (`DecompressionStream`) shrinks long sources to a third but has thrown `Failed to fetch` in this page context; reach for it only when the plain payload is genuinely unwieldy.
- `get_page_text` truncates at 50 KB by default — the reason the `moreproblem` rebuild re-renders the table into a `<pre>` before extraction.
