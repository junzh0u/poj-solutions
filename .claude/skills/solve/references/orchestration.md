# The parent's job

The parent owns everything shared: browser preflight, submit coordination, commits, `TODO`, and `attempts/`. It runs a pool of solve subagents and acts only on their reports — each problem passes through the parent as an id, a verdict, and file paths, never as content the parent reads and re-authors. `SKILL.md` covers the Claude-harness mechanics (loop, preflight, tab group); this file is the run policy.

## Selection and spawning

"Solve N problems" means: take the **top N ids of `TODO`** — the list is already ordered so the most-solved (roughly easiest and best-documented) come first — and work them. A specific problem id the user names overrides the ordering; hand its `attempts/<id>.md` to the agent if it has one, so it starts where the last run stopped. A single named problem is simply a pool of one with the same preflight, pinned browser, and commit path, not a different procedure.

Parked ids are not in `TODO` and come back exactly two ways: the user naming one, or `scripts/park-notes list --for-model <model-id>` reporting one as owed a retry on a model stronger than every model that has already tried it. Run that scan before the first spawn and put every id it prints in the earliest free slots, triaging anything it reports on stderr instead of ignoring it (see "What comes back, and when").

**Special Judge problems are gated and must not be spawned.** Before spawning an agent, run `scripts/spawn-precheck <id>`: `ok` clears it, `special-judge` (exit 3) means gate it — `scripts/park-notes gate <id> --gate special-judge`, then `scripts/commit-park <id> --subject '<id> gated under special-judge'` — and take the next id instead; any other failure is unknown state, not a clear. The gate is checked at spawn time rather than swept over `TODO` in advance, so it costs one fetch per spawn and writes a note only for ids a run actually reaches — a `TODO` sweep would mean thousands of fetches for problems nobody was going to attempt. The user lifts this gate (`park-notes ungate --gate special-judge` lists and, with `--delete`, releases); until they do, a Special Judge id is never worth an agent's time.

The gate exists because of what a special judge is: extra per-problem checker machinery that a plain diff does not have, and that can fail on its own. Six of the eight problems parked before this rule existed are Special Judge, all six on `judge`-kind evidence. That is a correlation rather than a proof, but it is strong enough to stop paying five submissions per problem to rediscover it. A gated id carries no verdict and no attempt: it is a policy hold, not a claim that the problem or its judge is broken, which is exactly why `gated` is its own park kind.

Spawn each agent with `subagent_type: poj-solver` and exactly the run-scoped state listed in `AGENTS.md` § "The interface" — the agent refuses to proceed without it. The model identifier is resolved once, at compose time, and pinned for the whole run: it goes in the pre-spawn `--for-model` scan, in every task prompt, and reaches each commit via the solver's `Model:` trailer, so a run that silently changed model midway would leave an archive that misattributes its own solutions. Nothing retires a model mid-run; the park record makes that unnecessary (below).

## Pool and refill

Run five agents by default; spawn the first batch one per problem, all in a single message so they start together, and from then on spawn a replacement from the top of `TODO` as soon as any one agent reports, without waiting for its siblings. Refill rather than wait, because a batch that waits for its slowest member sits idle for as long as that member runs — measured on 2026-08-06: ten of twelve problems resolved by 22 minutes, the batch ended at 36, and the freed slots sat empty the whole time. Each accept is committed the moment it lands, so a batch boundary is bookkeeping and nothing else.

A run with a target — "solve N problems" — needs a rule for when to stop refilling, because the pool can overshoot it. **Keep the pool full until the target is actually met by committed accepts**, then stop spawning and let the remaining agents drain. Do not taper earlier by spawning only as many agents as the target still needs: that assumes every agent in flight will accept, and one park then empties the pool short of the target and pays a fresh solve's wall clock to recover, serially, at the very end. The asymmetry decides it — an overshoot is an extra accepted problem off the top of the backlog, bounded by the pool size; an undershoot is dead time. When the pool does empty short, refill it and carry on. Never kill a live agent to stop on the number, either: it may already have clicked submit, and killing it there strands an Accepted submission with no archived source and no commit, which costs a submission to rediscover. (The 2026-08-06 run finished at 13 accepts against a target of 10, with all five draining agents accepting — exactly the case tapering gets away with, and which a single park would have broken.)

Five is a choice about the parent's own attention rather than a throughput ceiling: the parent has to read, commit, and respond to each verdict as it lands. Concurrency itself has headroom — twelve agents ran without saturating anything, and the submit lock's worst observed wait was 15 seconds against solves of 3 to 36 minutes. What does degrade with width is contention for POJ's ~10-second submission window: at sustained volume a dropped click is **routine** — a 2026-08-07 run of ~190 submissions through a pool of five lost about a dozen, near 6% — and the solver's own recovery procedure handles it. Raising the lock's 15-second interval to buy the drops back is a wash; the arithmetic is recorded so nobody re-derives it: ~12 drops at ~75 seconds of recovery each is some fifteen minutes, while adding five seconds to each of ~190 clicks costs about sixteen. Do not plan around the 6% either — another five-wide night put ~125 submissions through and lost none; it is variance, and expecting a drop is exactly what makes a site outage easy to misread as one.

## Acting on reports

**Accepted:** run `scripts/commit-accept <id> <commit-msg-file>` with the message file the report names. It stages `solutions/<id>` (source and any `test_data/`), strikes the id from `TODO` — or deletes `attempts/<id>.md` when the accept clears a park — and commits, all as one pathspec-limited commit, so each commit is the whole state change for one problem and `git status` is clean between accepts. Commit in whatever order the verdicts arrive, not `TODO` order; the commits are independent and `TODO` is a set, not a sequence.

On the accept path there is no review gate, and adding one back is the mistake this design prevents. The substance was certified by the judge, not by anything the parent could read: POJ returned Accepted, and the archived source is byte-identical to what was judged because its length was checked against the row's `Code Length`. The commit body is descriptive prose attached to an already-proven fact, in a repository that is not pushed, in git, amendable — so commit it unread. If a run does want assurance on an accept, the prose is the weakest test available: `scripts/status-via-curl <id>` confirms the reported run id and verdict against POJ itself in one command. Reading the body proves only that the agent can write.

**Parked:** the solver has already written the prose of `attempts/<id>.md`; the parent's job is the classification, which gates future work — `park-notes list --for-model` re-picks an id from the recorded kind, so `model` against `judge` decides whether the problem is ever retried at all. That judgment is about the run and the judge's public record, not about one solve, which is why it is the parent's call. Stamp it with `scripts/park-notes record <id> --model <model-id> --kind <kind> --submissions <n> --verdict '<verdict>'`, then `scripts/commit-park <id>`.

A **judge park** is the one hand-back to verify rather than take on trust, and the only one the parent can: every other park rests on the agent's own reasoning, but this one rests on a public page one command away. `scripts/verify-judge-park <id> --html-out <path>` reduces it to the counts that must hold — unrelated accounts failing the same way, no Accepted anywhere in the window — and the third condition, this account accepting other problems the same hour, is the run's own record. All three held for 1112 (13 System Error of the last 20 rows, five unrelated accounts, June–August 2026, four accepts by this account inside the same hour). Confirm the note records the numbers, then stamp with `--kind judge --recheck <status url>` (mandatory; the tool refuses a judge park without it).

**Infrastructure interruptions** (lost browser, logged-out session, structural rowless clicks, site outage) are not parks: no attempt notes, no barren-counter movement, the ids stay eligible. `SKILL.md` covers re-pinning a browser that dies mid-run. An agent that dies to a usage or rate limit has likewise attempted nothing — no write-up, no park, and the id keeps its place at the top of `TODO`; wait for the reset and rerun it.

Report each verdict to the user as it arrives rather than saving them for a summary, and commit in the same turn — under refill this is also what keeps the pool full.

## Parking: kinds and escalation

The note's front matter is the machine-readable park record, because "is this problem owed a retry?" used to be answered by a sentence in the body that a later run had to notice and interpret — and a note that never mentioned a model was indistinguishable from one with nothing left to try. `park` is the whole classification, and only `model` is ever re-picked automatically:

- `model` — the solve failed on reasoning or implementation, and a stronger model plausibly does better. 2125 is the worked example: five Wrong Answers on a statement ambiguity that a second reading resolved on the first retry submission.
- `judge` — POJ's judge or data is broken, on the evidence above. No model helps, so the retry is gated on the judge recovering instead: `--recheck` carries what would retire it.
- `infeasible` — neither. Nothing about the model or the judge will change the outcome.
- `gated` — a standing policy hold applied **before** the problem is attempted, so it is the one park with no attempt behind it and no verdict to record. Written by `park-notes gate`, never by `record`, which refuses `--kind gated`; the note carries `gate: <name>` instead of a `solvers` entry, and the tool refuses to write one over a note that already has real attempts. The only gate in force is `special-judge`.

`park-notes list --for-model <model-id>` prints the ids parked by a strictly weaker model, one per line — that is the whole re-pickup rule, and `references/model-ranks.txt` is the whole definition of "weaker". Nothing anywhere infers strength from a model name. A model missing from that file cannot park anything (`record` refuses it), and a note naming one is reported as **needing triage** on stderr with exit 4 rather than skipped — the ids on stdout are still valid, but a silent skip is exactly how an owed retry gets lost. Equal ranks mean no escalation in either direction, which is the honest encoding for two models whose relative strength has not been established here, notably across vendors.

When the stronger model fails too it does **not** get a second note: stamp its attempt over the existing one with the same `record` command, which appends a solver line and leaves `parked` at the original date. The id is then owed nothing until a model outranking *it* exists. If the retry is what uncovers a broken judge, pass `--kind judge --recheck <url>` and the park reclassifies in place. When a retry clears a park, the note is deleted in the accept's own commit (`commit-accept` does this) — a stale note left behind keeps offering a retry for a problem already solved.

A stronger-model retry runs under the higher submission cap (`AGENTS.md` § "The interface") and is spawned with the `attempts/<id>.md` path in its task prompt. The escalation has earned its keep: 2125 was the first id the scan ever handed back, and it was Accepted on the retry's first submission, on a statement ambiguity the official sample cannot distinguish. A second reading of the statement is worth more than a sixth submission of the first one.

Solve agents may run on a cheaper model than the parent to stretch the budget — most backlog problems don't need the strongest model. Which model is the run's own choice, and the user's whenever they name one. **A model park is not a problem park**: a problem the cheap model could not finish still deserves one run on a stronger model before the park is final. Inside a run that retry is just the next agent spawned into a free slot; across runs it is whatever `--for-model` reports as owed. Both read the same record, so the retry survives the run ending, a compaction, or a model switch weeks later — which is also why nothing ends a cheap model's run at its first park: the record already guarantees the retry, and stopping early costs the accepts the model would have gone on to make. Judge the model on its record, and let a park be a park.

`park-notes list` with no model shows every park as `owed` or `final`. That is a claim about future runs, not the current one: a run's own no-accept counter advances unless *that run* will itself retry the id on a stronger model. `park-notes check` validates every record; run it before trusting a listing, and in the same commit as any note you hand-edit.

## Stop conditions and safety

- Require a finite stop condition. A refilling pool has no batch boundary to count, so count resolved problems: default to stopping after **five consecutive resolutions with no Accepted solution**, one barren pool's worth. Reset the counter on any accept. A park counts toward it unless this run will itself retry the id on a stronger model.
- Treat usage limits, rate limits, and submission-path failures as interruptions, not verdicts: no notes, no counter movement, no replacement ids; resume the same ids after the reset.
- Preflight the submit path before spawning (see `SKILL.md`), pin the browser it selects for the whole run, and never let an agent substitute a target that merely looks available.
- Confirm external state before retrying anything interrupted — a submit click, browser error, or lost agent response can hide a submission that already landed.
- Do not push unless the user explicitly asks for that push.
