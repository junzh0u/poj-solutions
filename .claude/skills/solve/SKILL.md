# Work the backlog unattended

Read [references/orchestration.md](references/orchestration.md) completely before starting — it is the run policy: selection, spawning, pool and refill, acting on reports, parking, and the stop conditions. This file adds the Claude-harness mechanics: the loop, the browser, and the tab group. The parent↔solver interface is `AGENTS.md` § "The interface"; the solver's own procedure lives in `.claude/agents/poj-solver.md` and is not the parent's to read or paraphrase.

## Compose the loop

Invoke `/loop` with no interval so agent completions re-invoke the parent. The prompt must carry the complete run state because it is passed back verbatim on every firing and survives context compaction.

Default to a pool of five kept full by refill, and stop after five consecutive resolutions with no accept, unless the user specifies otherwise.

Keep run-specific state **out** of this baseline. A particular problem id baked into copy-paste text goes stale without anyone noticing, and the prompt beats the prose every time, because the prompt is what actually runs. Say what the run should *do*; let it read what is currently *true* from the repo, and let this run's own choices come from the user. The solver-model default below is the one deliberate exception: a standing choice recorded here with its rationale, revisited when the cost baselines change, not leftover state from a past run.

```text
/loop keep 5 solve agents in flight, refilling each slot from the top of TODO as soon as an agent reports rather than waiting for its siblings. Stop when 5 consecutive resolved problems produce no accept. Spawn subagents with <the model the user named, or claude-sonnet-5 if they named none> and keep that model for the whole run. Before the first spawn, run `.claude/skills/solve/scripts/park-notes list --for-model <the model id the solve agents will run>` and put every id it prints in the earliest free slots, triaging anything it reports on stderr instead of ignoring it. Check every id with `spawn-precheck` before spawning and gate the special-judge ones. Act on each report per references/orchestration.md: `commit-accept` each accept and stamp-and-`commit-park` each park in the turn it arrives. A usage or rate limit is not a park: do not create attempt notes or advance the no-accept counter; wait for the reset and retry the same ids. Report each verdict as it arrives. Do not push.
```

The model is the user's call; when they don't make it, spawn the solvers on **`claude-sonnet-5`** — the cheapest per accept of the Claude models measured in [references/run-costs.md](references/run-costs.md), and most backlog problems don't need a stronger model, while the park record guarantees a stronger-model retry for the ones that do. The parent stays on the session model; only the agents default. Whichever way it is resolved, resolve it **once**, at compose time, and pin it — it goes in the pre-spawn `--for-model` scan, in every task prompt, and reaches each commit via the solver's `Model:` trailer, so a run that silently changed model midway would leave an archive that misattributes its own solutions.

The refill needs no scheduling machinery: a finishing agent already re-invokes the parent, so the turn that reads a verdict is the turn that commits it and spawns its replacement. Do that in the same turn — a slot left empty until the next wakeup is the idleness this design exists to remove. Spawn nothing when `TODO` is empty or the stop condition has been met, and let the remaining agents drain.

Adapt the pool size, stop condition, and model policy to the user's request without dropping the safety rules in the orchestration reference. A user who asks for a number of *solves* rather than a barren-stretch stop ("stop after 10 solved") is setting a target, so keep the barren-stretch condition as a safety net underneath it and follow the reference's endgame: keep the pool full until committed accepts reach the target, then drain rather than kill. Put both conditions and the drain rule in the loop prompt, since that is what survives compaction — a run amends its own stop condition by re-arming `ScheduleWakeup` with an updated prompt, which is the mechanism for changing run state mid-run.

## Preflight the submit path

Do this once before spawning — a logged-out session looks to each agent like an individual failure, and every agent in the pool would burn its run discovering it. It costs one tab, which then becomes the keepalive tab below. A failed preflight is an infrastructure stop: no attempt notes, no movement of the no-accept counter, the ids stay eligible.

Preflight is also where the browser gets chosen, and choosing is the **parent's** job, once. If the tools report several connected Chromes, probe them: only one Chrome may hold the POJ login, so a missing submit form on the first device is not yet a verdict on the session. Navigate a tab to `http://poj.org/submit?problem_id=<first id>` and read `document.forms.length` and `document.forms[2].problem_id.value`: three forms with a matching id is a live session, one form is the login page. Pin the `deviceId` of the browser that shows the logged-in form. Unattended runs pick that way too rather than asking — `list_connected_browsers` wants a user choice, and a `/loop` parent has no user to ask. Only when no connected Chrome holds the login is it an infrastructure interruption. Loaded browser tools with no connected Chrome are not a submission path either — check that a browser is actually attached before reading the form.

The `deviceId` is the whole pin, and the only part worth relaying: `tabs_create_mcp` takes no arguments and puts its tab in the connected browser's single MCP tab group, so there is no window or group an agent could be told to target. It is run-scoped state the agents cannot rediscover for themselves, so it goes in every task prompt — including every agent spawned into a refilled slot — and stays fixed for the whole run, even if the user opens another window or profile.

## Re-pin a browser that dies mid-run

Losing the pinned target mid-run is a stop for the **agents**, not for the run: the parent can re-preflight and re-pin, and the agents resume where they stopped — none of them has submitted from an unverified session, so none has to be unwound. Nothing is re-solved and no attempt is consumed. An agent reporting a lost browser target is a request for a new one, not a verdict on its problem; only when no reachable Chrome holds the login is the run actually stopped, and that is the point at which the ids stay eligible and the run ends without notes.

- Re-run `list_connected_browsers`, `select_browser`, then navigate and read the form exactly as in preflight. A crashed-and-restarted Chrome comes back under a **new `deviceId`**, so the old id is gone even though it is the same browser and the same profile — do not read its absence as the session being lost. On 2026-08-06 the pinned id vanished and the replacement was still logged in, with the parent's keepalive tab and its tab group both intact across the crash.
- Push the new id to **every live agent** with `SendMessage`, and record it as the pin for every agent spawned afterwards. An agent that stopped and reported the loss is resumed from its transcript with its finished solve still in context and needs only the new id to continue at its submit step; an agent still working gets the message queued to its next tool round and picks the id up before it reaches submit. Both paths were exercised in one batch — two resumed, three queued, all five submitted normally, four Accepted on their first submission.
- Say in the message that the loss was infrastructure and that no attempt was consumed, so the agent does not spend its own reasoning re-deriving whether its cap or its solve is intact.
- Re-state the keepalive tab id and that it must not be closed. A resumed agent re-reads the tab group and will otherwise see a tab it did not create.

## Own the tab group's lifetime

The parent and every solve agent share **one** MCP tab group per Claude Code session, and closing what the extension counts as its last tracked tab auto-removes the group (`Closed tab N. Group is now empty (auto-removed).`). Removing a Chrome tab group does **not** close the tabs inside it — it ungroups them, and `tabs_close_mcp` then refuses them (`Tab N is not in this session's tab group`), so an orphaned tab is beyond every tool here and only the user can close it. Concurrent agents make this routine rather than rare, because the auto-remove decision races sibling `tabs_create_mcp` calls.

So the parent holds a **keepalive tab** in the group: open it before spawning the first agent (the preflight tab serves), keep it for the whole run, close it only after the pool has drained and the last agent has reported. A group that never reaches zero tabs is never auto-removed. A refilling pool makes this more load-bearing, not less — slots turn over continuously, so there are far more moments where an agent's close would otherwise be the group's last. Measured across two five-agent batches: without the keepalive, 9 tabs created and 4 orphaned; with it, every tab closed and the group auto-removed exactly once, on the parent's own final close, which is where that removal is harmless. A refilling run of 13 agents confirmed it end to end — 13 tabs created, 13 closed, group removed once at the very end. A last `tabs_context_mcp` before that final close is the cheap confirmation, and it should show the keepalive tab alone.

The keepalive tab's **id is not stable across a long run**. On a 118-problem run the id was silently reassigned mid-flight — the group id was unchanged, the tab was still on the parent's own preflight URL, and only the number had moved. The tab is identified by the group plus the URL it is parked on, not by an id an agent memorised hours earlier. Re-read `tabs_context_mcp` and adopt the new id, then hand it to every later spawn, rather than concluding the keepalive is gone and opening a second one. The check is cheap and worth doing whenever an agent reports the keepalive missing from its context.

Agents will report tabs they did not create. Sibling churn means a `navigate` can spawn a tab another agent then adopts, and stale tabs disappear from the group on their own — both have been reported and both were benign, reconciling against the sibling's own created/closed pair. Treat such a report as an observation to match up in the final ledger, not as a leak.

Do not audit agent tabs from the parent by id while the pool is running. Membership of the shared group flickers as agents create and close tabs, and a parent reading it mid-run can see the full set, a stale subset, or no group at all — none of which is evidence about any particular agent. Audit at the end of the run instead: every report carries the tab ids the agent created and closed; accumulate them as they arrive, and treat created-minus-closed as the leak count. Report any leak to the user with the ids, since only they can clear it.

## Recover from stalls

Use `ScheduleWakeup` only as a fallback for a hung agent or rate-limit reset, never as the refill mechanism — refill happens in the turn a verdict arrives, not on a timer. For a normal hung-agent fallback, schedule 1800 seconds.

A hung agent is more expensive under refill than under batching, because it holds a slot open indefinitely instead of merely delaying a boundary. When the fallback fires and one agent is still out, check whether it is actually working before treating it as hung: `scripts/status-via-curl <id>` shows any submissions it has already made, and its scratchpad subdirectory shows whether artifacts are still being written. On 2026-08-06 an agent that looked stalled at the 30-minute mark had four Wrong Answers and a fresh status baseline three minutes old — it was mid-solve on its final attempt, and killing it would have thrown away a completed write-up. When resuming an agent that stalled by ending its turn on a background wait, have it read the status page first — it may already have a submission judged, and resubmitting on top of it wastes an attempt.

On a usage limit, arm the wakeup before refining the reset time because the environment may be partially unavailable. `ScheduleWakeup` caps at one hour, so chain wakeups for a longer reset. When the loop resumes, inspect status before resubmitting; the interrupted turn may already have landed a submission.

Report verdicts as they arrive rather than saving them for a summary, and commit each accept in the same turn you report it — a verdict held for a tidier batch summary is a verdict the user did not get. Under refill this is also what keeps the pool full, so batching up the bookkeeping stalls the run itself.
